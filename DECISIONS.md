## 13/11/2026 — démarrage de la production

- **Symfony 7.4 LTS** (et non 8.x, pourtant disponible) : le brief demande 6.4 ou 7.x ; 7.4 est la version à support long, la plus durable dans cette fourchette.
- **Angular 22** (dernière stable), composants autonomes et signaux, sans zone.js (défaut des nouveaux projets).
- **PHP cible 8.4** (`config.platform.php` dans `composer.json`) : certaines dépendances exigent 8.4 ; l'hébergeur devra le proposer (à vérifier chez AlwaysData).
- **Composer lancé via `composer.sh`** : sur ce Mac, Composer plante (segfault) dès qu'il télécharge, parce que la libcurl Homebrew tente HTTP/3 et que la combinaison ngtcp2 + OpenSSL 4.1 plante dans `SSL_set_quic_tls_cbs`. Le script désactive `curl_multi_exec`, ce qui fait passer Composer par les flux PHP (sans HTTP/3). À retirer quand Homebrew aura corrigé curl / ngtcp2.
- **Tests de l'API sur SQLite** (rapides, jetables). Au démarrage, la base de dev était aussi en SQLite car MySQL local ne démarrait plus (`mysqld` cherchait `libprotobuf-lite.35.1.0.dylib`, supprimée par une mise à jour Homebrew de protobuf) : voir la réparation ci-dessous.
- **13/11/2026, réparation de MySQL local** (accord de Yoann) : plutôt que `brew reinstall mysql` (qui aurait installé MySQL 26.10, montée de version majeure du dossier de données partagé avec EcoRide et GameZone), installation de `mysql@9.7` (9.7.4, même série, compilée contre le protobuf actuel) et `brew link` de cette version. Sauvegarde préalable : `/opt/homebrew/var/mysql-sauvegarde-2026-11-13`. MySQL a fait seul la mise à niveau 9.7.1 → 9.7.4 ; EcoRide et GameZone intacts. Base `planning` + utilisateur dédié `planning` (mot de passe dans `api/.env.local`). La base de dev est désormais MySQL ; les tests restent sur SQLite. Pas de démarrage automatique : `mysql.server start` après un redémarrage du Mac.
- **Identifiants UUID v7** générés par le serveur : permettent l'annulation à l'identique et ne révèlent pas le nombre de lignes.
- **Annulation côté serveur** (`UndoLog` + opérations inverses) plutôt qu'un instantané côté front : le serveur reste la seule source de vérité, et l'annulation est testable.
- **Chaque modification renvoie le planning complet** : un seul appel, zéro désynchronisation ; acceptable vu le volume.
- **Doublons exacts ignorés** (même jour, cabinet, infirmière, durée) aussi depuis la fenêtre « Ajouter N jours » (le prototype ne le faisait qu'en mode glisser).
- **Infirmière obligatoire si le cabinet en a** : vérifié côté serveur, comme dans le prototype côté écran.
- **Pense-bêtes** : une seule table `Note` avec une portée (jour, cabinet, infirmière) au lieu de listes dans chaque objet.
- **Vacances scolaires** : table `school_holiday` alimentée par `data/vacances-scolaires.json` (`app:holidays:import`), une mise à jour par an. Jours fériés calculés (Pâques), rien à mettre à jour.
- **Pas de « données d'exemple » ni « Repartir de zéro » dans l'application** : c'était propre au prototype (données locales). Les données de démonstration passent par les fixtures Doctrine (`doctrine:fixtures:load`, compte `demo@planning.test`, mot de passe dans `.env.local`).
- **« Mot de passe oublié ? »** : affiche « Demandez à Yoann de vous créer un nouveau mot de passe » (`app:user:create` change le mot de passe d'un compte existant). Pas d'envoi d'e-mail pour l'instant.
- **Jeton JWT valable 30 jours** : l'application reste ouverte sur le téléphone. « Rester connectée » décoché → jeton oublié à la fermeture.
- **Déploiement visé : front et API sur le même domaine** (build Angular copié dans `api/public`) : pas de CORS en production, un seul HTTPS.
- **13/11/2026, mise en ligne sur AlwaysData** : site `projetplanning.alwaysdata.net`, PHP 8.4, MariaDB 11.8. Racine du site = lien `~/www` → `~/planning/api/public` (l'ancien dossier est gardé dans `~/www-origine`). Front compilé sur le Mac et envoyé par `rsync` (le build n'est pas dans git) ; API installée par `git clone` + `composer install --no-dev`. Accès SSH par clé dédiée (`~/.ssh/id_ed25519_alwaysdata`), aucun mot de passe dans le chat ni dans git : `.env.local` est écrit sur le serveur par un script qui demande le mot de passe de la base en masqué et génère les autres secrets.

## 16/11/2026 — premiers retours de l'utilisatrice

Trois demandes après les premiers jours d'utilisation, traitées dans l'ordre demandé.

- **1. Pense-bêtes dans la fiche d'un cabinet.** Constat : on ne créait un pense-bête de cabinet que depuis la vue jour (« Rattacher à : un cabinet ») ou dans « Modifier le cabinet », et la fiche (Mon activité → un cabinet) n'en montrait aucun. Ajout d'une section « Pense-bêtes » juste sous les compteurs : ceux du cabinet, puis ceux de ses infirmières avec leur nom (fonction pure `cabinetNotes()`), bouton « Ajouter un pense-bête » qui crée un pense-bête déjà rattaché au cabinet (la fenêtre pense-bête sait maintenant créer). Pas de changement d'API : le planning renvoyait déjà tous les pense-bêtes ; tests ajoutés (contenu, isolation entre comptes).
- **Modifier un pense-bête est maintenant annulable** (c'était le seul « Enregistrer » sans « Annuler » avec la fiche cabinet), pour respecter la règle « annulation après chaque modification ». Reste non annulable : « Enregistrer le cabinet » (envoyé en bloc), à revoir si besoin.
- **2. Balayer pour changer de période.** Gestes `touch*` sur la zone qui défile plutôt qu'une bibliothèque : peu de code, et la décision (seuils 60 px et 1,5 × le vertical, bords de 20 px, mode ajout, fenêtre ouverte, onglet « Mon activité ») est une fonction pure testée. Petite animation (Web Animations, 180 ms), coupée si l'appareil demande moins d'animations. La sélection de jours vides est gardée d'un mois à l'autre. **Non testé sur un vrai iPhone** (vérifié avec des touchers simulés dans le navigateur).
- **3. Cabinets actifs / en veille.** Booléen `active` sur `Cabinet` (vrai par défaut) plutôt qu'une date de fin : c'est ce que l'utilisatrice décrit (« activer / désactiver »), et l'historique reste entier puisque rien n'est supprimé ni déplacé. Route dédiée `PUT /api/cabinets/{id}/active` (annulable) plutôt qu'un champ de plus dans « Enregistrer le cabinet », qui n'est pas annulable. L'interrupteur du formulaire appelle cette route après l'enregistrement. Le serveur refuse un nouveau jour dans un cabinet en veille, y compris en déplaçant un jour existant vers lui ; modifier ou supprimer un jour déjà placé reste possible. Le front garde le cabinet d'un jour qu'on modifie dans les choix, même en veille. Confirmation seulement s'il reste des jours prévus, sans bloquer. La légende ne montre plus que les cabinets ayant des jours dans la période visible (actifs ou non).
- **Non fait, en attente de l'accord de Yoann** : proposer automatiquement la mise en veille quand le dernier jour prévu est passé.
- **Correctif d'affichage trouvé en route** : les boutons placés directement dans un écran rétrécissaient (jusqu'à 25 px de haut) dès que la page défilait, parce que les écrans sont des composants en `display: contents`. Règle `#main>*>*{flex-shrink:0}`.
- **Migration `Version20261116000000`** (`ALTER TABLE cabinet ADD active TINYINT(1) DEFAULT 1 NOT NULL`) : les cabinets existants deviennent actifs, rien d'autre ne change. Vérifiée sur la base MySQL locale (4 cabinets, tous actifs, schéma en phase). En production, la base est **sauvegardée avant** la migration (données réelles), et la migration passe **avant** l'envoi du nouveau front.
- `docs/retours-utilisatrice.md` reste hors du dépôt public (comme `BRIEF.md`) : il cite l'utilisatrice.
